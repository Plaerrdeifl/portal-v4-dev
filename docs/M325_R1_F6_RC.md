## 2. Verbindlicher Umsetzungsumfang

### 2.1 Private Mitfahrerlisten

M325-R1 führt wiederverwendbare private Mitfahrerlisten ein.

Dabei gilt:

- die Listen gehören einem konkreten Portalnutzer,
- Autorisierung erfolgt owner-basiert,
- der Portalnutzer bleibt bei einer Buchung die Hauptperson `PRIMARY`,
- gespeicherte Personen werden ausschließlich als `COMPANION` verwendet,
- es entsteht keine Proxy-Buchungsfunktion für fremde Hauptpersonen,
- es wurde keine neue globale Capability eingeführt.

Private Mitfahrerlisten sind nicht öffentlich lesbar.

### 2.2 Duplicate Preview

Vor einer Buchung mit gespeicherten Mitfahrern kann eine kontrollierte Duplicate Preview durchgeführt werden.

Mögliche Ergebnisse sind:

- `READY`
- `ALREADY_REGISTERED`
- `CONFLICT`

Die Preview gibt keine unnötigen personenbezogenen Details bestehender Anmeldungen preis.

Die eigentliche Buchung vertraut nicht ausschließlich auf die Preview. Vor der finalen Speicherung erfolgt eine erneute serverseitige Prüfung.

Eine gemeinsame Buchung wird atomar verarbeitet. Es gibt keine Teilbuchung einzelner Teilnehmer.

### 2.3 Gruppenbuchung und Warteliste

Für gemeinsame Buchungen gilt:

- die gesamte Gruppe wird `ACTIVE`, oder
- die gesamte Gruppe wird `WAITLISTED`.

Eine teilweise Aktivierung einer gemeinsamen Buchung ist nicht vorgesehen.

Die bestehende FIFO-Grundlogik der Warteliste bleibt erhalten.

### 2.4 Strukturierte Zustiegsorte

M325-R1 ergänzt strukturierte Zustiegsorte über folgende Datenbereiche:

- `fanbus_boarding_stops`
- `fanbus_trip_boarding_stops`
- `fanbus_bus_boarding_stops`

Wenn für eine Fahrt aktive strukturierte Zustiegsorte existieren, muss jede neu angemeldete Person einen gültigen Zustiegsort auswählen.

Teilnehmer derselben gemeinsamen Buchung dürfen unterschiedliche Zustiegsorte verwenden.

Eine Buszuweisung ist nur zulässig, wenn der ausgewählte Bus den Zustiegsort des Teilnehmers tatsächlich bedient.

### 2.5 Registrierungserweiterung

Die Fanbusregistrierung wurde unter anderem ergänzt um:

- `trip_boarding_stop_id`
- `operational_note`
- Companion-Provenienz

Für `operational_note` gilt eine maximale Länge von 240 Zeichen.

### 2.6 Fahrtbetrieb und Check-in

M325-R1 enthält einen operativen Check-in für die Hinfahrt.

Check-in-Art:

- `OUTBOUND`

Statuswerte:

- `OPEN`
- `PRESENT`
- `NO_SHOW`

Änderungen sind revisionsbasiert und verwenden `expectedRevision` zur Konkurrenzkontrolle.

Operative Zähler berücksichtigen ausschließlich aktive Teilnehmer.

### 2.7 Berechtigungen

Die bestehenden Fanbus-Berechtigungen bleiben unverändert:

- `fanbus.manage`
- `fanbus.registrations.manage`

Für private Mitfahrerlisten gilt zusätzlich die owner-basierte Autorisierung.

Es wurde keine neue globale Capability eingeführt und das zentrale Berechtigungsmodell wurde durch M325 nicht erweitert.

### 2.8 Routing

Die bestehenden Fanbus-Routen bleiben erhalten.

M325-R1 enthält keinen Router-Refactor.

## 3. Effektive Fahrtkapazität – F5 Round 2

Im Rahmen der F5-Abnahme wurde die Kapazitätslogik verbindlich präzisiert.

Die wirksame Fahrtkapazität entspricht:

> Summe der Kapazitäten aller aktiven Busse der Fahrt.

Dabei gilt:

- inaktive Busse zählen nicht zur wirksamen Kapazität,
- der Server ist autoritativ,
- es existiert keine zweite Kapazitätsberechnung im Browser,
- 0 aktive Busse ergeben eine effektive Kapazität von 0,
- eine Fahrt mit 0 effektiver Kapazität kann weiterhin als Entwurf verwaltet werden,
- eine Veröffentlichung mit effektiver Kapazität 0 wird blockiert,
- eine spätere Kapazitätsreduzierung demoted bereits bestehende `ACTIVE`-Teilnehmer nicht,
- die Wartelisten-Promotion verwendet die effektive Kapazität,
- es wurde keine neue automatische Promotion-Policy eingeführt.

Serverseitiger Helper:

`app_private.fanbus_effective_capacity(p_trip_id uuid)`

Der Helper ist default-deny abgesichert und nicht direkt für Browserrollen freigegeben.

## 5. F5 Round 3 – Post-Success Capacity Refresh

### 5.1 Gefundener Nachbefund

Beim Live-E2E wurde festgestellt, dass eine erfolgreich gespeicherte gemeinsame Anmeldung den serverseitigen Bestand korrekt veränderte, die bereits geladene Fahrtkarte jedoch zunächst den alten Kapazitäts-Snapshot anzeigte.

Beispiel aus dem ersten Live-E2E:

- vor Buchung: 98 von 100 Plätzen frei,
- 2 Teilnehmer erfolgreich gebucht,
- DB danach: 96 von 100 Plätzen frei,
- Fahrtkarte zeigte ohne Reload weiterhin 98 von 100.

Die Buchung selbst war korrekt und vollständig gespeichert. Der Fehler betraf ausschließlich die Aktualisierung der bereits dargestellten Fahrtkarte.

### 5.2 Korrektur

Round 3 korrigiert ausschließlich dieses Anzeigeverhalten.

Nach einer akzeptierten Anmeldung gilt nun:

1. die Erfolgs- bzw. Wartelistenbestätigung wird zuerst angezeigt,
2. anschließend wird die Fahrt server-autoritativ über den bestehenden `loadTrip()`-Pfad erneut geladen,
3. der globale Fahrt-Snapshot wird durch die neue Serverantwort ersetzt,
4. die Fahrtkarte wird neu gerendert,
5. die bereits angezeigte Erfolgsbestätigung bleibt bestehen.

Ein Fehler beim nachgelagerten Anzeige-Refresh:

- macht eine erfolgreiche Buchung nicht zu einem Fehler,
- öffnet die Formulare nicht erneut,
- verändert die Buchungssemantik nicht.

Es wurde keine lokale Kapazitätssubtraktion im Frontend eingeführt.

Die Korrektur gilt für Gast- und Portalpfad.

## 9. Bekannter Baseline-Hinweis zu `portal_core.sql`

Es wird ausdrücklich **nicht** behauptet, dass `portal_core.sql` global vollständig grün ist.

Der direkte Gesamtlauf von `portal_core.sql` endet mit Exitcode 3.

Ursache ist ein bestehender/staler Baseline-Testharness: Bei seiner Bereinigung wird `app_modules.events` gelöscht, obwohl eine Fanbus-Trip-Fixture auf einen entsprechenden Event-Datensatz verweist.

Bewertung:

- bekannte Baseline-/Testharness-Schuld,
- kein nachgewiesener M325-R1-Funktionsregress,
- targeted M320/M325-pgTAP ist erfolgreich,
- innerhalb M325 wurde bewusst kein fachfremder Framework- oder Harness-Fix vorgenommen.

Daraus folgt ausdrücklich nicht die Aussage, alle SQL-Tests hätten bestanden.

Empfohlener Status:

`M325_R1_RELEASE_CANDIDATE = READY`

- DEV-Abnahme abgeschlossen,
- RC technisch vorbereitet.

`READY` bedeutet ausdrücklich nicht:

- PROD deployed,

- eine neue Produktentscheidung getroffen,
- Finance-Integration abgeschlossen.
