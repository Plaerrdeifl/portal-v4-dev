# M000-R1-C – Processes and logging

Package C adds the bounded local process foundation for M000-R1. It does not add check orchestration, productive check files, a passed overall operator run, deployment, or any package-D function.

## Implemented files

- `scripts/operator/modules/Operator.Process.psm1` owns the immutable target registry, fixed launch resolution, worker gate, Job Object, bounded stream capture, timeout/health handling, process results, and run completion.
- `scripts/operator/Operator.ProcessWorker.ps1` validates its fixed parameters, resolves the registered target again, waits for the local gate, starts the target, relays both streams, and writes the atomic start and completion records.
- `scripts/operator/test-fixtures/Process.Fixture.ps1` provides only the ten fixed, non-networked fixture modes.
- `Operator.Security.psm1`, `Operator.Reporting.psm1`, and `portal-operator.ps1` provide redaction, closed atomic process reports, and package-C initialization.

## Registry and launch contract

The registry contains exactly four NPM targets and nine public fixture targets. NPM targets are allowed only in `LocalVerify`/`LocalFreeze`; fixtures are allowed only in `SelfTest`; no target allows `Preflight`. Timeout profiles remain `short` 15 seconds, `standard` 60 seconds, and `long` 300 seconds. Only the two health fixtures use `stdout-token` with the exact token `M000_PROCESS_HEALTH_READY_V1` and a five-second health timeout.

Invalid or unknown target IDs are rejected before sequence, directory, gate, job, worker, or PID creation. Their closed return object contains only fixed rejection metadata and `<redacted>`. The registry validator compares all 13 entries, ordered arrays, health definitions and implementation mappings against the complete approved matrix without coercion. Registered targets resolve exclusively to the trusted Windows PowerShell 5.1 fixture path or to `node.exe` plus the Node-installation-derived `npm-cli.js`; `package.json` is read as strict UTF-8 through a 1,048,576-byte stream bound, and the selected script must be a real non-empty string. No manifest can provide paths, arguments, environment, health logic, or timeout seconds.

## Worker, gate, and Job Object

The manager creates a unique `Local\` manual-reset event, starts the fixed worker with `powershell.exe -File`, creates a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and assigns the worker before signaling the event. The worker cannot start a target before that signal. The target and its descendants inherit the job membership. Cleanup queries and terminates only that job; it never searches or kills by process name.

The worker writes an atomic, closed `control.json` after target start. After the target has exited and both relayed streams have completed successfully, it writes a second atomic, closed and transient `completion.json` containing the unchanged target exit code, then exits with worker code zero. The manager accepts a target exit code only from a completion record whose exact fields, types, registered target, distinct positive PIDs and UTC timestamp match the validated start record. A non-zero worker code, a missing record or an invalid record is an internal process error with no target exit code. Gate and both control records are removed independently in `finally`; timeout and failed health checks do not require completion.

Every run has the fixed local mutex `Local\Plaerrdeifl-M000-RunLock-<RunId>`. An attempt acquires it for at most 330 seconds before sequence allocation and holds it through preflight, worker and target execution, cleanup, logs and `process.json`. Initialization and run completion use the same mutex, so a used run cannot be reset and aggregation cannot overlap an active attempt. An abandoned mutex transfers ownership only after the complete existing-attempt set has passed the same integrity validation.

## Streams, health, and limits

stdout and stderr are drained concurrently and remain separate. Each in-memory buffer is bounded to 5,242,880 characters while excess input continues to be consumed. Redaction, normalization and line bounding run before the final total bound is applied; the structured preparation result reports both `text` and the effective `truncated` state. A truncated log, including its complete `[TRUNCATED:stream-limit]` marker, never exceeds that limit. Health checks search only the transient bounded stdout buffer and require the target to remain a member of the job when the token is observed.

Every captured stream passes through `Protect-OperatorLogText` before a write. One call removes ANSI and forbidden controls, normalizes newlines, redacts private keys, JWTs, GitHub/Supabase tokens, passwords, connection credentials, URL userinfo, forbidden project refs and reserved success markers, bounds lines, then repeats the sensitive-value check. Control-split values are therefore redacted in one pass and the result is idempotent. Run completion reads each `process.json` through a 65,536-byte stream bound and each process log through a fixed UTF-8 byte bound; an oversized or invalid member aborts aggregation before either valid run-level log or `cleanup.json` is replaced.

## Reports and cleanup

Each started or registered blocked attempt uses `processes/<sequence>-<targetId>/` with atomic UTF-8-without-BOM `stdout.log`, `stderr.log`, and closed `process.json`. Before a new sequence or completion, every existing entry must be a lückenlose, uniquely sequenced registered-target directory containing exactly those three completed artifacts, passed cleanup and zero remaining processes; foreign files, transient records and incomplete or manipulated attempts are integrity errors. Run-level logs use fixed 5,242,880-character `StringBuilder` buffers. Headers and the single complete truncation marker count toward the bound, while all later logs continue to be bounded-read and validated without being retained.

Normal completion allows up to five seconds for natural job exit before forced cleanup. A target without a health check may already have exited after its valid control record; its validated completion record remains authoritative. Health token acceptance still requires current job membership. Timeout, health, and internal failures terminate the unique job immediately and verify it for up to five seconds. Job termination and verification, job-handle disposal, gate disposal, both control-file removals, stream completion and worker-handle disposal are attempted independently. A worker whose job assignment failed is terminated only through its known handle, retried once, and checked after each attempt; if it remains alive, counters report at least one remaining owned process, cleanup fails and status is blocked.

All durable process writers accept only the canonical `%LOCALAPPDATA%\Plaerrdeifl\PortalOperator\runs\<RunId>` hierarchy and its exact `processes\<sequence>-<registered-target>` children. The run root, run directory, process directory and every existing parent segment must be local, canonical and reparse-free; UNC, device, network and look-alike `processes` paths are rejected. The worker repeats the same containment checks before opening the gate or starting a target.

## Validation

Windows PowerShell parsing, registry exactness, NPM static resolution, rejection cases, quoting, stream separation, exit codes, health success/failure, timeout, child-tree termination, output truncation, redaction, atomic reporting, repeated runs, and foreign-process survival were exercised without Pester. Portal regression retained `blocked/20`, `error/30`, and skipped run cleanup as specified, with no success marker.

## Package boundary and known blockers

The complete check orchestrator, M000 check files, manifest `M000-R1.json`, Pester acceptance, successful SelfTest, LocalVerify, LocalFreeze, and deployment remain package D or later. Package C does not claim M000-R1 completion. No package-C implementation blocker is known.
